# 00 — Overview

## 1. Purpose

**Modern-Client.v2** recreates Counter-Strike 1.6, and only Counter-Strike 1.6 ([ADR-0017](adr/0017-counter-strike-only.md)),
from scratch, as open source, with **behavior identical to the original** from the point of view
of players and server operators. Underneath, the
engine is modern, parallel and free of the fixed caps of GoldSrc.

The project has three pillars:

1. **Parity:** movement, weapons, economy, rounds, maps, HUD, console, cvars and servers
   behave as in CS 1.6. A veteran player should not "feel" any difference, except for
   more stability and performance.
2. **No historical limits:** entities, precache, players, messages, mods and threads
   no longer have arbitrary caps built into the format or the protocol.
3. **First-class plugins and mods:** the model the community already knows is kept
   (plugins loaded by the server, grouped into mods), but with new technology. Plugins
   are written in **Rook**, a new, strongly typed language with a syntax familiar to
   those coming from AMX Mod X/Pawn, compiled by its **own modern compiler** (`rookc`),
   with a stable, versioned API decoupled from the engine.

## 2. Limits of the original and how the project removes them

| Limit in CS 1.6 / GoldSrc | Consequence | Approach in Modern-Client.v2 |
|----------------------------|--------------|-------------------|
| Legacy code (Quake/GoldSrc, C/C++98) | Hard to maintain, unsafe, coupled | C++26 from scratch, modules, typed errors, contracts, tests ([02](02-coding-standards.md)) |
| A single thread for simulation, rendering and networking | Idle modern CPUs, frame spikes | Job System with work-stealing and a chunk-parallel ECS ([04](04-job-system.md), [03](03-ecs.md)) |
| Entity caps (edicts and visible entities per packet, such as the famous 512) | Large maps and mods break with "no free edicts" or entities vanish | 32-bit generational entity IDs, with no structural cap; networking with interest management and a per-client budget ([03](03-ecs.md), [08](08-networking.md)) |
| Limited precache (models, sounds and generic resources at around 512 each) | Mods must choose which resources to load | Resource registry with no cap, on-demand loading and incremental download ([06](06-assets-and-resources.md)) |
| A maximum of 32 players | Large modes are impossible | `maxplayers` from 1 to **1024** (default 32), a policy cap and not a format cap ([09](09-dedicated-server.md)) |
| Small user messages (≈192 bytes) | Truncated mod HUDs and menus | Typed messages of any size, with fragmentation and a budget ([08](08-networking.md)) |
| Content limits: 4 attachments per entity, `body` packed into a few bits, 256-color paletted sprites of limited size, and bones, vertices, controllers and blends with fixed caps | Limited mod weapons and models, low-quality HUD and effects | Dynamic structures, attachments by name, body groups per part, high-resolution RGBA sprites (`.nxspr`) ([06 §3.4](06-assets-and-resources.md#34-removed-content-limits)) |
| 1-byte HUD and network fields (health, ammo, clip…) | Health above 255 shows up wrong on the HUD (e.g. zombies and bosses in mods) | Values with the domain types of the game (`Health`, `Armor`, `Money`), with no artificial cap, encoded as varints, and a HUD with no digit limit ([12](12-ui-hud-and-console.md#34-no-value-truncation)) |
| AMXX/Pawn: untyped 32-bit cell, weak tags, no structs, strings in fixed buffers | Silent bugs, verbose code | Rook: nominal types, structs, enums with data, `Result`, units of measure ([14](14-rook-language.md)) |
| Mods coupled to memory offsets (pev, private data, Orpheu) | They break with every update | Declarative API generated by reflection from the engine, versioned with semver ([15](15-mod-api.md)) |
| Server-only mods, with no prediction | Custom weapons feel "choppy" with lag | `shared` Rook code runs on the server and on the client, with a sandbox and prediction ([13](13-mod-system.md)) |
| Reloading a plugin requires a map change | Slow development | Hot reload with typed state migration ([13](13-mod-system.md)) |

## 3. Goals

- **G1 — Gameplay parity:** faithfully reproduce CS 1.6, latest Steam version, including
  movement (bunny hop with its penalty, duck jump, strafe, surf, ladders), ballistics,
  spread, recoil and penetration.
- **G2 — Server parity:** server operators recognize everything:
  `server.cfg`, `mapcycle.txt`, `motd.txt`, `mp_*`/`sv_*` cvars, `rcon`, `status`, `kick`,
  `banid`, command-line parameters, the server browser and A2S queries.
- **G3 — Scale:** from 1 to 1024 players, tens of thousands of entities and unlimited
  resources. Degradation is predictable and configurable, with no crash and no hidden limit.
- **G4 — Performance:** use every available core, with a stable frame time and minimal
  input latency.
- **G5 — Native mods:** the Rook language, a complete, typed API, tools (LSP,
  debugger, formatter, tests) and hot reload.
- **G6 — Engineering quality:** decoupled modules, typed errors, no magic numbers,
  automated tests, CI on Windows and Linux.

## 4. Non-goals (for now)

- **Half-Life and other GoldSrc games:** no Half-Life single player, no Half-Life Deathmatch,
  no other GoldSrc game and no engine abstraction for them
  ([ADR-0017](adr/0017-counter-strike-only.md)). Mods are Counter-Strike 1.6 mods.

- **Binary compatibility with GoldSrc:** protocol 48 and the original clients/servers
  are not compatible with Modern-Client.v2. The limits of the original are built into that
  protocol (see [ADR-0008](adr/0008-own-network-protocol.md)).
- **Loading `.amxx`, `mp.dll`, `client.dll` or Metamod plugins:** mods are migrated to
  Rook ([16](16-amxx-migration.md)). Assisted conversion tools may exist.
- **Distributing Valve assets:** the game works with free content and, if the user owns
  CS 1.6, uses their local installation, configured almost automatically
  ([ADR-0015](adr/0015-free-content-and-optional-original-assets.md)).
- **Mandatory visual remaster:** the default look is the original one. Improvements are
  optional, through a cvar (`r_fidelity`).
- **Kernel-level anti-cheat.** Security relies on an authoritative server and validation.

## 5. Principles

1. **Parity first, extension later.** Every new feature must preserve the original
   behavior when configured with the default values.
2. **No arbitrary limits.** When a limit exists (memory, bandwidth, security), it is
   named, configurable and documented, and reaching it produces a typed, observable
   error.
3. **Explicit instead of magic.** No silent fallback, no hidden global state, no magic
   numbers. Gameplay values live in versioned data.
4. **Decoupled APIs.** Modules depend on interfaces, never on internal details. The mod
   API is a stable facade over the engine.
5. **Errors are values.** Expected failures are types (`std::expected` in C++, `Result` in
   Rook). Invariant violations are contracts.
6. **Determinism where it matters.** The same build and the same inputs produce the same
   simulation, which makes replays, parity tests and debugging possible.
7. **Parallel by default, serial by decision.** Batch work runs in jobs. Game rules with
   a meaningful order run in a fixed, documented order.
8. **Evolution in small, complete steps.** Each milestone delivers something playable and
   tested ([19](19-roadmap.md)).

## 6. Audiences and use cases

| Audience | Main use case |
|---------|-----------------------|
| Player | Play CS 1.6 with the same feel, on modern hardware and systems |
| Server operator | Start `nextds` with the same configs and commands as always |
| Mod developer | Write mods in Rook with strong typing, hot reload and a debugger |
| Mapper | Use the existing BSPs and current compilers (ZHLT/VHLT) without changing the workflow |
| Engine contributor | Work on isolated, well-tested C++26 modules |

## 8. Success metrics

- A veteran player cannot tell the movement apart from the original in a blind test (bhop,
  strafe, recoil, spread).
- `de_dust2` with 32 players runs at a 100 Hz tick using a fraction of one core on the
  server.
- A stress test with 1024 simulated players runs without a crash, with degradation
  controlled by the network budget.
- ReZombie (the reference mod), ported to Rook, ends up smaller, more readable and free of
  casts.
- Zero leaks and zero data races in the tests with sanitizers.
