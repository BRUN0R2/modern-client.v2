# 15 — Plugin API

## 1. Overview

The API is the **stable facade** between Rook plugins and the engine/game. Principles:

- **Decoupled:** plugins never see internal structures. The bindings layer
  (`nx.script`) translates stable names and types to the internal C++, so refactoring the
  engine does not break plugins.
- **Generated, not handwritten:** annotated C++ functions and types
  (`[[=nx::script::Native{"precacheModel"}]]`) generate, through reflection, the call
  *thunks* and the **`.rookd`** declaration files (equivalent to `.inc`) used by `rookc`
  and the LSP.
- **Familiar:** the `get*Var`/`set*Var` pattern, forwards and hooks in the AMXX/ReAPI
  style, with camelCase names like the whole project (`getWeaponVar`, `precacheModel`), and
  AMX Mod X's own spelling through the `amxx` compatibility layer (`register_clcmd`,
  `get_player_var`; [ADR-0021](adr/0021-rook-amxx-names.md)).
- **Typed end to end:** no raw indices, no string flags (`"ae"`), no
  `message_begin`/`write_byte`.

## 3. Forwards

The error type of the lifecycle forwards is chosen by the plugin, as long as it is an
`error enum`.
For convenience, `cs.prelude` defines `PluginError`, an `error enum` with a `from`
variant for each API error. It allows using `?` on any call without declaring an enum of
your own and stays fully typed.

| Forward | Signature | AMXX equivalent |
|---------|-----------|-----------------|
| `pluginPrecache` | `() -> Result<void, E>` | `plugin_precache` |
| `pluginInit` | `() -> Result<void, E>` | `plugin_init` |
| `pluginCfg` | `() -> Result<void, E>` | `plugin_cfg` |
| `pluginEnd` | `()` | `plugin_end` |
| `pluginPause` / `pluginUnpause` | `()` | same |
| `clientConnect` | `(player: Player)` | `client_connect` |
| `clientAuthorized` | `(player: Player, identity: PlayerId)` | `client_authorized` |

| `clientInfochanged` | `(player: Player)` | `client_infochanged` |
| `serverFrame` | `()` | `server_frame` / `FM_StartFrame` (prefer `@system`) |
| `roundFreezeStart` | `()` | `HLTV` event |
| `roundStart` | `()` | `logevent round_start` |
| `roundEnd` | `(reason: RoundEndReason, winner: Team?)` | `logevent round_end` |
| `playerSpawned` | `(player: Player)` | `Ham_Spawn` post |

| `hostageRescued` | `(hostage: Entity, rescuer: Player)` | — |

## 4. Handles and var catalogs

Handles form a hierarchy: `Player` and `Weapon` are also `Entity`, so
`getEntityVar(player, "origin")` works. The list below is the initial one. The full
catalog is generated by `rook doc`.

Each accessor has its underscored spelling too, the same function: `get_entity_var`,
`set_player_var`, `get_weapon_class_var`… ([ADR-0021](adr/0021-rook-amxx-names.md)).

| `armor` | `Armor` | read/write |
| `gravity`, `friction` | `Scale` | read/write |
| `maxSpeed` | `Speed` | read/write |
| `model` | `Model?` | read/write |
| `skin` | `i32` | read/write |
| `body` | `i64` | read/write (legacy combined value, for compatibility only) |
| `renderMode` | `RenderMode` | read/write |
| `renderFx` | `RenderFx` | read/write |
| `renderAmount` | `RenderAmount` | read/write |
| `renderColor` | `Color` | read/write |
| `solid` | `SolidType` | read/write |
| `moveType` | `MoveType` | read/write |
| `takeDamage` | `DamageMode` | read/write |
| `owner` | `EntityRef?` | read/write |
| `flags` | `Flags<EntityFlag>` | read/write |

| `nextThink` | `GameTime` | read/write |

Body groups and attachments have no cap ([06 §3.4](06-assets-and-resources.md#34-removed-content-limits))
and are accessed by **name**:

```rook
setBodyGroup(entity, "scope", ScopeVariant.Holographic.submodel())?;   // Result<void, ModelError>
let muzzle: Vector3? = getAttachment(entity, "muzzle");
let parts = getBodyParts(model);                                      // List<BodyPartInfo>
```

A nonexistent body part, submodel or attachment name produces a `ModelError` with the list
of valid names.

### 4.4 `WeaponClass` — `getWeaponClassVar` / `setWeaponClassVar`

**Original and custom weapons use the same system.** The 26 CS weapons are classes
registered by the game (constants `WEAPON_AK47`, `WEAPON_AWP`…), and changing the AK's
price is the same as configuring a new weapon. The design follows ReZombie's weapon API
(classes, inheritance, virtuals and per-instance data without spending entities).

| Key | Type | Access |
|-----|------|--------|
| `name` | `string` | read/write |
| `type` | `WeaponType` | read |
| `parent` | `WeaponClass?` | read |
| `abstract` | `bool` | read |
| `slot` | `WeaponSlot` | read |
| `viewModel`, `playerModel`, `worldModel` | `Model` | read/write |
| `price` | `Money` | read/write |
| `maxClip`, `maxAmmo` | `AmmoCount` | read/write |
| `ammoType` | `AmmoType` | read/write |
| `weight` | `i32` | read/write |
| `canDrop` | `bool` | read/write |
| `maxSpeed` | `Speed` | read/write |
| `damage` | `Damage` | read/write |
| `fireInterval` | `Duration` | read/write |
| `rangeModifier`, `armorRatio` | `Scale` | read/write |
| `penetration` | `Penetration` | read/write |
| `teams` | `Set<Team>` | read/write |

```rook
let rifle = createWeaponClass("drakar_iii", WeaponType.Primary, parent: WEAPON_AK47)?;
setWeaponClassVar(rifle, "name", "Drakar III");
setWeaponClassVar(rifle, "viewModel", precacheModel("models/rezombie/weapons/drakar/v.mdl")?);
setWeaponClassVar(rifle, "maxClip", AmmoCount(45));
bindWeaponVirtual(rifle, WeaponMethod.PrimaryAttack, onDrakarAttack);

fn onDrakarAttack(weapon: Weapon, owner: Player) -> WeaponReturn {
    return callWeaponBase(weapon, owner);     // run the parent implementation (AK-47)
}
```

- `bindWeaponVirtual` checks at compile time that the function has the signature the
  method requires (`WeaponMethod.PrimaryAttack → fn(Weapon, Player) -> WeaponReturn`).
- `shared` plugins with weapon classes also run on the client, with **prediction**
  ([13 §7](13-mod-system.md#7-plugins-on-the-client)).

### 4.6 Plugin catalogs

API plugins declare their own catalogs ([14 §13.2](14-rook-language.md#132-variable-catalogs-vars)).
ReZombie, for example, defines `vars Class`, `vars Props` and `vars Mode`, and the content
plugins use `setClassVar`, `setPropsVar` and `setModeVar` with the same type checking as
the engine.

## 5. Hookable actions

Equivalent to ReAPI (`RegisterHookChain`) and Ham Sandwich. All of them have a `Pre` and a
`Post` phase.

| Hook | Main arguments | What `Pre` can do |
|------|----------------|-------------------|
| `ClientConnect` | `address`, `identity`, `name` | Reject with a reason (`args.reject = some("...")`) |
| `ClientCommand` | `player`, `command` | Block |
| `ChatMessage` | `player`, `inout text`, `teamOnly` | Change or block (antiflood, filters) |
| `PlayerSpawn` | `player` | Block or adjust |
| `GiveDefaultItems` | `player` | `Supercede` to give its own items |
| `PlayerTakeDamage` | `victim`, `inflictor`, `attacker?`, `inout damage: Damage`, `source`, `hitGroup` | Change or block |
| `PlayerTraceAttack` | `victim`, `attacker`, `inout damage`, `direction`, `hitGroup` | Change or block |
| `PlayerKilled` | `victim`, `killer?`, `source`, `gib` | Adjust (e.g. no gib) |
| `PlayerJump`, `PlayerDuck` | `player` | Block |
| `PlayerResetMaxSpeed` | `player`, `inout maxSpeed: Speed` | Change the speed |
| `PlayerMove` | `player`, `inout movement: MovementParams` | Custom movement (`shared` code, predicted) |
| `ChooseTeam` | `player`, `inout team` | Force or block |
| `PlayerAddMoney` | `player`, `inout amount: Money`, `reason` | Change or block |
| `BuyItem` | `player`, `item`, `inout price: Money` | Change the price or block |
| `ItemPickup` | `player`, `item` | Block |
| `WeaponDrop` | `player`, `weapon` | Block |
| `BombPlant` / `BombDefuseStart` / `BombDefuseEnd` / `BombExplode` | `player?`, `bomb` | Block and adjust timings |
| `RoundRestart` | — | Adjust |
| `RoundEnd` | `inout reason`, `inout winner`, `inout delay: Duration` | Change or block |
| `CheckWinConditions` | — | `Supercede` for custom rules (game modes) |
| `EntitySpawn`, `EntityThink`, `EntityTouch`, `EntityUse` | `entity`, `other?` | Block |
| `EntityTakeDamage` | `entity`, `attacker?`, `inout damage` | Change or block (`func_breakable` etc.) |
| `EmitSound` | `entity`, `channel`, `inout sound`, `inout volume`, `inout pitch` | Replace or block sounds |
| `SetModel` | `entity`, `inout model` | Replace models |

## 6. Other API areas

### 6.1 Players with typed filters

```rook
// AMXX: getPlayers(players, count, "ae", "TERRORIST")
let terrorists = getPlayers(PlayerFilter { alive: some(true), team: some(Team.Terrorist) });
```

### 6.2 Resources

```rook
let model: Model = precacheModel("models/rezombie/zombie.mdl")?;   // Result<Model, ResourceError>
let sound: Sound = precacheSound("rezombie/infect.wav")?;
```

They can be called **at any time** (no limit). In `pluginPrecache`, they become mandatory
downloads. Afterwards, they are delivered on demand. `rookc` checks literal paths against
the mod's and the game's assets and warns at build time if the file does not exist.

### 6.3 Effects (no `message_begin`/`write_byte`)

```rook
createBeam(BeamEffect {
    start:    getEntityVar(player, "origin"),
    end:      targetPosition,
    sprite:   LASER_SPRITE,
    width:    BEAM_WIDTH,
    color:    Color.GREEN,
    duration: 200ms,
});
screenFade(player, ScreenFade { color: Color.RED, duration: 500ms, hold: 0ms });
```

### 6.4 HUD, chat and menus

```rook
showHudText(player, HudText { message: tr("RZ_ROUND_START"), position: HudPosition.TOP_CENTER, hold: 3s });
clientPrintColor(allPlayers(), "{green}[RZ]{default} {name} was infected!");

showMenu(player, Menu<ModeChoice> {
    title: tr("RZ_MENU_MODES"),
    items: [
        MenuItem { label: "Infection", value: ModeChoice.Infection },
        MenuItem { label: "Nemesis",   value: ModeChoice.Nemesis, enabled: isAdmin },
    ],
    onSelect: onModeSelected,       // fn(Player, ModeChoice), no raw key numbers
});
```

The color tags of `clientPrintColor` are checked at compile time.

### 6.5 Client commands

There is no arbitrary `client_cmd`: in AMXX it was used to change the player's binds and
configs without permission (*slowhack*). Client-side actions come from specific APIs (play
a sound, open a menu, change the FOV) or from sandboxed client plugins.

### 6.6 Storage

```rook
let store = kvOpen("rezombie_stats")?;                       // capability `storage`
kvSet(store, playerKey(player), PlayerStats { infections: 10, kills: 3 })?;
let stats: PlayerStats? = kvGet(store, playerKey(player))?;
```

SQLite uses prepared queries with parameters and rows mapped to structs, without
concatenating SQL.

## 7. Networking

Plugins define typed messages, without the size cap of the original's user messages:

```rook
@message(channel: Channel.Reliable)
pub struct InfectionNotice {
    victim:   PlayerRef,
    attacker: PlayerRef?,
    class:    ClassId,
}

sendMessage(allPlayers(), InfectionNotice { victim: refOf(victim), attacker: none, class: ZOMBIE });

// client plugin
@onMessage
fn onInfection(notice: InfectionNotice) { ... }
```

The message schema goes into the protocol schema hash ([08 §10](08-networking.md#10-versioning)).

## 8. Logging and diagnostics

- `logInfo`, `logWarn` and `logError` automatically include the plugin, file and line.
- Normal gameplay logs should go to the mod's diagnostics plugin (ReZombie's
  `DevRuntime` pattern). The linter warns about `logInfo` on hot paths.

## 9. Error catalog

All of them are `error enum`s with a default message. The engine's are generated through
reflection from the C++ `enum class`es.

| Error | Variants (examples) |
|-------|---------------------|
| `ResourceError` | `NotFound{path}`, `InvalidPath{path}`, `UnsupportedFormat{path}`, `TooLarge{path, limit}` |
| `EntityError` | `UnknownClassname{name}`, `QuotaExceeded{limit}`, `NotAlive` |
| `ModelError` | `UnknownBodyPart{name, valid}`, `UnknownSubmodel{part, index}`, `UnknownAttachment{name, valid}` |
| `WeaponClassError` | `NameTaken{name}`, `ParentNotFound{name}`, `AbstractNotGivable{name}`, `IncompatibleType` |
| `CommandError` | `AlreadyRegistered{name}`, `InvalidName{name}` |
| `CvarError` | `AlreadyExists{name}`, `OutOfRange{value, min, max}`, `ReadOnly{name}` |
| `HookError` | `AlreadyRegistered`, `UnknownHook` |
| `MenuError` | `Empty`, `PlayerNotConnected` |
| `StorageError` | `CapabilityMissing`, `Corrupted`, `QuotaExceeded`, `SchemaMismatch{key}` |
| `HttpError` | `CapabilityMissing`, `HostNotAllowed{host}`, `Timeout`, `Status{code}` |

## 10. Versioning and stability

- The API follows **semver** (`api = "^1.0"` in `mod.toml`).
- Each item has a stability level:
  - `@stable`: changes incompatibly only in a major version;
  - `@experimental`: requires `experimental = true` in `mod.toml`;
  - `@deprecated(since: "1.4", use: "newFunction")`: produces a compile warning with the
    alternative and is removed only in the next major version.
- CI compares the generated `.rookd` files with those of the last release and **blocks**
  incompatible changes in minor versions, the `amxx.*` modules' and the underscored accessors
  included.
- `rook doc --api` publishes the complete API reference, with tested examples.
