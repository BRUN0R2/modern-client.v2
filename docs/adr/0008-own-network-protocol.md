# ADR-0008 — Own network protocol, not compatible with protocol 48

- **Status:** Accepted
- **Date:** 2026-10-20

## Context

GoldSrc's protocol 48 embeds the limits the project wants to remove: entity and precache
indices with few bits, small user messages, 1-byte HUD fields and a cap on entities per
packet. It also has no encryption and uses plain-text RCON. At the same time, servers need
to "work like the old one": cvars, commands, A2S queries and server browsers.

## Decision

- **Own protocol** over UDP, with a stateless cookie handshake, encrypted sessions
  (libsodium), reliable/unreliable channels, fragmentation, delta snapshots generated by
  reflection, interest management and a per-client budget ([08](../08-networking.md)).
- **Operational compatibility** with the original: the same network cvars, prediction,
  interpolation and lag compensation, **A2S** queries on the same port and logs in the HLDS
  format.
- **No** compatibility with GoldSrc clients or servers.

## Alternatives considered

| Alternative | Why not |
|-------------|---------|
| Implement protocol 48 | Would inherit every limit and the insecurity, and would require reverse engineering undocumented parts |
| GameNetworkingSockets | Solid, but it takes over the socket (which hinders A2S and connectionless packets on the same port) and brings large dependencies |
| ENet / yojimbo | Useful, but the core of the value (replication, interest, compensation) is the project's own anyway, and the transport is small |

## Consequences

- ✅ No caps on entities, resources and messages, and secure by default.
- ✅ Monitoring tools keep working through A2S.
- ⚠️ Original CS 1.6 clients do not connect (accepted as a non-goal).
- ⚠️ Transport and encryption require care. Mitigation: libsodium, fuzzing and a security
  review before the release.
